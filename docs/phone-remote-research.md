# A phone companion for the TV browser

Researched 2026-10-10. This is a feasibility assessment and product recommendation, not an implementation or a device-tested compatibility claim. Product examples below are first-party descriptions; they were not installed or audited.

**Yes: scan a QR code, open a web page on an iPhone or Android phone, and use it to operate the actual browser running on the TV.** The most useful first version would put an address/search field, keyboard, touchpad, scrolling, back/forward, and tabs on the phone. The TV would keep the real website, cookies, media playback, and browsing session. Seeing and directly tapping that TV page on the phone is also feasible, but adds a separate screen-streaming problem.

## What already exists

- **DDTv Browser** advertises a phone touchpad reached by scanning a QR code, controlling its TV cursor, scroll wheel, menu, and back action. This is a close browser-specific precedent, although its public description does not establish its transport, security, or reliability. [DDTv official site](https://www.ddtvbrowser.top/)
- **BetterSTR TV** describes a QR code opening an iPhone/Android browser remote with directional buttons, playback, and text entry, without an app installation. Its stated connection is direct over the property's Wi-Fi, and capabilities depend on the TV software. This establishes the app-free interaction pattern; it is a managed TV product rather than a general browser. [BetterSTR announcement](https://betterstr.com/blog/2026/09/21/phone-remote-for-your-tv)
- **Google TV** supports pairing with a TV code, typing with the phone keyboard, swiping, and playback control through Google Home/Google TV apps. **Apple TV** has a paired iPhone/iPad remote and same-network setup. These validate the controls, but their native phone integrations are different from our proposed web companion. [Google instructions](https://support.google.com/chromecast/answer/11221499?hl=en), [Apple instructions](https://support.apple.com/en-nz/108778)
- **YouTube's TV code** can link a phone when it is on a different Wi-Fi network. Its companion controls a specific YouTube experience; Google explicitly says mobile-browser youtube.com cannot cast. This is evidence for cross-network pairing, not an API for operating arbitrary TV websites. [YouTube pairing documentation](https://support.google.com/youtube/answer/7640706?hl=en-GB)

TV Bro's official feature list establishes a browser optimized for a physical TV remote, but does not establish this QR phone-control feature. It should not be cited as a verified equivalent. [TV Bro source repository](https://github.com/truefedex/tv-bro)

## Three different experiences

1. **Phone as controller:** look at the TV, move its pointer with the phone, type on the phone, and select tabs there. One TV browser session does the browsing. This is the recommended starting point.
2. **TV page visible on the phone:** stream the TV browser's rendered page to the companion; phone taps map back to TV coordinates. This supports the stronger “do it all while looking at my phone” interpretation. It requires capture, compression, streaming, and input mapping.
3. **Phone browser mirrored or synchronized:** screen mirroring makes the phone the rendering device. Opening the same URL in two browsers creates separate sessions unless a website supplies synchronization. Neither automatically gives phone control over the existing TV browser.

An ordinary companion website cannot simply embed every destination in an iframe and control it. Browser origin boundaries restrict access to another site's content, and sites can reject framing with `frame-ancestors`. Different screen layouts and independent session state further undermine generic click replay. This is why the TV app needs an explicit control integration, or the phone needs a stream of the TV-rendered page. [HTML cross-origin access rules](https://html.spec.whatwg.org/multipage/nav-history-apis.html#cross-origin-objects), [CSP framing controls](https://www.w3.org/TR/CSP/#directive-frame-ancestors)

## Recommended first experience

**Recommendation:** make “Use your phone” a visible TV-browser action. It shows a short-lived QR code and a manual pairing fallback. Scanning opens an HTTPS companion, identifies the TV, and establishes an authenticated connection. Show the connected phone on the TV with an immediate disconnect action.

Start with an address/search bar, a large touchpad with tap-to-click and scrolling, back/forward/reload, and open/switch/close tabs. When a text field is active, offer phone text entry. Return the actual TV title, address, selected tab, and connection state so the phone never silently claims an action succeeded. Keep the existing TV remote usable.

The TV remains the source of truth: commands target a particular tab and current page state; reconnection refreshes that state before accepting more input. Stop movement when the connection dies, and reject stale input after navigation or a tab change. These are proposed behaviors, not features currently present.

**Project fit:** local Brave source at `e41398dd15d0ed111a814e408e775ce75eb0f564` already routes browser navigation, pointer hover, taps, and scrolling through `TvBrowserControls`; `TvRemoteInput.Target` provides a small boundary for physical-remote input. Those are plausible reuse points. They are not existing network APIs. The reviewed TV directory has no identified phone pairing or transport implementation. Preserve its native-UI, lifecycle, and private-tab access guards when introducing a separately authenticated command boundary. [TvBrowserControls](../brave/android/java/org/chromium/chrome/browser/tv/TvBrowserControls.java), [TvRemoteInput](../brave/android/java/org/chromium/chrome/browser/tv/TvRemoteInput.java)

Typing needs more than sending individual key codes: selection, Unicode, composition, deletion, and focus changes must work. Android's `InputConnection` has explicit text and composition operations; adapting Chromium's active input connection is a candidate that requires validation. [Android InputConnection API](https://developer.android.com/reference/android/view/inputmethod/InputConnection)

## How the phone reaches the TV

**HTTPS companion plus a secure WebSocket relay — recommended initial transport.** Both phone and TV establish outbound connections to a public service, which routes authenticated messages between them. This avoids inbound home-router configuration and phone-to-LAN access as requirements, and can work while the phone uses cellular data. It introduces a service dependency, hosting cost, and a network round trip. WebSocket supplies bidirectional transport and TLS support; pairing, end-to-end encryption, expiry, and authorization remain application responsibilities. These tradeoffs are architectural inferences from the client/server protocol. [WebSocket specification](https://datatracker.ietf.org/doc/html/rfc6455)

**TV-hosted LAN HTTP/WebSocket server — useful if offline/local operation is a requirement.** The QR can point directly to the TV's address, and the TV can serve both UI and commands. Same-origin local hosting avoids some public-site-to-private-network complications. However, phone and TV need network reachability: cellular data, guest-network isolation, changing addresses, TLS certificate trust, and browser policy need explicit handling. Plain HTTP delivers both credentials and executable companion code without transport protection; adding encryption only to later commands cannot protect a tampered client. LAN does not automatically mean trusted.

**WebRTC — attractive for a later live view.** A peer connection can carry video plus control data, attempting a direct route using ICE/STUN and using TURN when a relay is necessary. It still needs a signaling channel and authenticated peer identity. Data channels use SCTP over DTLS and support different delivery modes, but encrypted transport alone does not authenticate the intended TV. This has more setup and operational machinery than routing small command messages over WebSocket. [WebRTC connection guide](https://webrtc.org/getting-started/peer-connections), [WebRTC data-channel standard](https://www.rfc-editor.org/info/rfc8831/)

Current browser restrictions make a universal LAN promise unsafe:

- Chrome's newer Local Network Access permission replaces the earlier Private Network Access approach. Its original blog contains an obsolete statement that WebSockets are not gated: **Chrome 147 release notes explicitly include WebSocket permission prompts for local addresses.** Secure-context rules and some Chrome-specific mixed-content exemptions also apply. [Chrome LNA explanation](https://developer.chrome.com/blog/local-network-access), [Chrome 147 release notes](https://developer.chrome.com/release-notes/147)
- Chrome 154 adds a WebSocket `targetAddressSpace` option for qualifying local mixed-content exemptions. This is version-specific evidence, not a cross-browser baseline. [Chrome 154 release notes](https://developer.chrome.com/release-notes/154)
- Safari requires its own verification. WebKit's LNA implementation tracker is still open, while Safari Private Browsing can ask before revealing an IP address to a local server. Neither fact proves every LAN connection fails or every Chrome exception applies to Safari. [WebKit tracker](https://bugs.webkit.org/show_bug.cgi?id=250607), [WebKit Private Browsing documentation](https://webkit.org/blog/15697/private-browsing-2-0/)

Consequently, test actual Safari/iOS and Chrome/Android versions, denied permissions, phone background/resume, and network changes. Standards and release notes do not substitute for that matrix.

## Seeing and tapping the actual TV page

Chrome DevTools already demonstrates the underlying capability: its Android screencast accepts clicks as touch events, keystrokes, and scrolling against the remote page. It also documents two limitations: the stream excludes native browser/system UI, and screencasting reduces frame rate. This is strong feasibility evidence, but developer tooling is not a shipping phone-control product. [Chrome's Android screencast documentation](https://developer.chrome.com/docs/devtools/remote-debugging#screencast_your_android_screen_to_your_development_machine)

**Recommendation:** test optional live view after basic control works. Capture the actual TV viewport, fit it to the phone with zoom, and translate touches using the current frame's geometry and identity. A small TV preview is still a wide desktop page, not automatically a comfortable mobile layout. Measure readability, input delay, CPU, heat, and video playback on the target ARM TV hardware before choosing capture resolution or transport. Keep TV audio on the TV unless a separate listening feature is desired.

Browser-owned capture and Android `MediaProjection` are different implementation routes. MediaProjection requires user consent for each session and has single-use token rules on Android 14+. Secure surfaces/protected video buffers can be absent from captures; TV playback working does not guarantee a DRM video can appear in the phone preview. [Android media projection](https://developer.android.com/media/grow/media-projection#user_consent), [Android secure surfaces](https://developer.android.com/reference/android/view/Display#FLAG_SECURE)

## Pairing, privacy, and the limits of “everything”

**Recommended security design:** the QR carries an expiring invitation plus high-entropy pairing material, not a permanent public remote URL. Bind the resulting controller to the intended TV, consume the invitation once, allow revocation, and require a fresh pairing for new controllers. Rate-limit any human-entered short code. OAuth device-flow guidance is relevant precedent for code entropy, expiry, and guessing defenses; this does not mean OAuth itself is required. [RFC 8628 security considerations](https://www.rfc-editor.org/rfc/rfc8628.html#section-5)

Use TLS and authenticated end-to-end encryption for control/state payloads if the relay should not read URLs, text, or frames. Authenticate the key exchange against the QR material, prevent replay, validate command scope, and omit text/frame payloads from logs. A QR secret in a URL fragment can avoid sending that secret in the initial HTTP request, but client JavaScript can still read it: trustworthy companion delivery and excluding third-party scripts remain necessary. [URI fragment semantics](https://datatracker.ietf.org/doc/html/rfc3986#section-3.5) End-to-end encryption protects against a forwarding relay reading payloads; it does not eliminate trust in the web-client host, which supplies the executable code.

Other boundaries remain:

- **Trusted input and dialogs:** JavaScript-dispatched events are not equivalent to physical input for user-activation-gated APIs. Use the browser's native input path, test fullscreen/playback and permission prompts, and preserve explicit approval for sensitive native actions. [HTML user activation rules](https://html.spec.whatwg.org/multipage/interaction.html#tracking-user-activation)
- **Accounts and passwords:** the TV keeps its own signed-in session. Pairing does not transfer phone cookies or unlock its password manager. A companion origin cannot generally use arbitrary sites' passkeys; relying-party identity and origin checks still apply. Site-supported login QR flows or properly supported cross-device authentication are separate integrations. [Passkey identity binding](https://developers.google.com/identity/passkeys/), [Authentication verification](https://developers.google.com/identity/passkeys/developer-guides/server-authentication)
- **Private browsing and system access:** exclude locked private tabs, secrets, and unintended screen areas from exported state. Keep permission dialogs visible and scoped. Do not expose ADB, an unrestricted DevTools endpoint, arbitrary JavaScript execution, or control of unrelated TV apps as the companion protocol. These are design recommendations for the expanded trust boundary.

The next useful experiment is a paired web companion that opens URLs, moves/clicks/scrolls, switches tabs, and commits real Unicode text on one TV. Validate reconnection and privacy boundaries on real iPhone/Android browsers. A separate live-view experiment should then determine whether direct tapping feels good enough to justify the extra capture and streaming work. No implementation effort or latency estimate is established by this research.
