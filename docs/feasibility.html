Research as of 8 October 2026 · Source and documentation review

A TV browser built from Brave

Proceed with an Android TV feasibility prototype. Fork Brave’s Android application and adapt its interface and input handling while preserving its Chromium and Shields integration.

Defer a native Apple TV browser. Brave’s iOS app does not provide a supported shortcut to tvOS. Apple’s public web-view availability and App Store rules make this a separate, substantially constrained project.

This research inspected upstream documentation, release metadata, and selected source files. It did not compile Brave, install an APK, measure performance, or obtain store approval. Engineering estimates below are planning judgments, not measured results.

The strongest evidence

On 16 May 2025, a Brave maintainer reported having compiled and loaded Brave on a Fire TV. They identified support for TV controls as remaining work and closed the feature request as unplanned. This establishes a concrete precedent; it does not establish that the current release works on every TV. Maintainer’s comment.

The latest release returned by Brave’s release API during this review was v1.97.56, published 7 October 2026, using Chromium 155.0.8059.40. It includes Android APKs for several architectures. Brave’s current support page requires Android 10 or newer; older cached pages still mention Android 8. The pinned Chromium configuration also defaults to API 29. Release; current requirements; Chromium configuration.

Keep the integration inside Brave’s Android application and build system.

Architecture proposal informed by the Brave Core architecture and Android TV adaptation guide. Reuse still requires device validation.

The source to fork is brave/brave-core. The brave-browser repository primarily holds releases, issues and documentation. Brave Core supplies Chromium patches, Android integration and the Rust ad blocker. This is a full browser build, not a conventional small Gradle project or a documented drop-in “Brave WebView” SDK. Repository overview.

ApproachAssessment
Adapt Brave’s existing Android appRecommended. Preserves the most working browser and Shields integration. Requires a disciplined, relatively small set of downstream changes.
Build a new shell around extracted Brave internalsPossible in principle, but creates more integration work around profiles, permissions, tabs, services and Chromium upgrades. Consider only if the existing activity becomes a demonstrated obstacle.
Start with a TV WebView browser and add adblock-rustA fallback for a different scope. Reuses Brave’s matching engine, but does not inherit full Shields behavior or Brave’s browser integration.

The adblock-rust library supports network and cosmetic rules, resource replacements and scriptlet resources. An application still has to enforce its decisions in the network and page contexts. Android WebView’s interception API has documented gaps, including certain URL schemes and redirect handling, so wrapping a WebView is not equivalent to retaining Brave’s integration. adblock-rust; WebView interception API. TV Bro provides an existing open-source reference for remote-oriented browser UX; its existence does not establish Brave compatibility.

The actual Android TV work

  1. Install and launch: add a TV launcher activity or entry point, banner and icon; declare touchscreen and absent hardware optional; check the generated manifest, startup and first-run flow. These are necessary packaging changes, not the complete port. TV setup requirements.
  2. Browser controls: make the address bar, tabs, bookmarks, Shields settings and all prompts usable from across the room. Every actionable element needs visible focus and a reliable route back to the browser controls.
  3. Website interaction: use directional focus for the browser UI and prototype a remote-controlled pointer for arbitrary webpages. Include deliberate scrolling and a clear mode indicator. JavaScript sites, nested scrolling, menus, video overlays, forms and embedded frames make “map arrows to Tab” insufficient. Deliver pointer actions through the browser’s own input path; evaluate reliability on actual sites.
  4. Text and login: preserve the TV’s system keyboard and available dictation, support ordinary form fields and password dialogs, and consider authenticated phone-to-TV URL entry later. Do not make a phone mandatory for core use.
  5. Media: validate hardware decoding, fullscreen, play/pause, seek, audio focus, screensaver behavior, captions and resume after sleep. Chromium’s existing media stack is a starting point; each device and service still needs testing.
  6. Limited hardware: profile release builds on a modest device as well as a faster one. Set a conservative active-tab policy, restore suspended tabs, and measure startup and memory. A large Chromium engine remains a large engine after changing the toolbar.
  7. Scope control: start with browsing, bookmarks/history, a small tab switcher, private sessions and a usable per-site Shields toggle. Defer Wallet, Rewards, VPN, Leo, News and account/sync features. Use supported feature controls where possible; hiding UI does not prove that background services stopped.

Google requires five-way D-pad operation, suitable Back behavior and controls that do not depend on a dedicated Menu button. These constraints should drive the interaction design from the first prototype. TV app quality requirements.

Concrete source areas to inspect when implementation starts
  • BraveActivity.java: Brave’s Android activity integration.
  • BraveTabbedActivityClassAdapter.java: rewrites Chromium activity inheritance and redirects selected constructors. This demonstrates why a standalone new Android shell would not simply inherit all Brave behavior.
  • Chromium manifest patch and Brave Android build configuration: entry points and dependency integration.
  • components/brave_shields: ad-blocking services and enforcement. Preserve this integration initially.

Paths linked to master describe files inspected in the development tree and may drift. Implementation should pin a current stable release and confirm the corresponding files. Prefer isolated TV resources and small hooks over wholesale replacement of upstream layouts; Brave’s own Android guidance discusses the upgrade burden of large replacements.

Ad blocking, video and services

The valuable part is reusable. Retaining the full Brave browser preserves the existing native Shields integration as the baseline. However, blocking also depends on fresh filter lists, scriptlet resources and component updates. Test first install, restart, offline behavior and a subsequent list update. A blocking counter alone is not proof that all protections work. Brave component and filter endpoints; filter-list packaging.

Protection applies to pages opened in this browser. It does not remove ads from other installed TV applications. Do not promise permanent ad-free playback on any specific service: website behavior and anti-blocking measures can change. Maintain a visible, remote-accessible per-site override for broken pages.

For protected video, distinguish ordinary HTML5 playback from DRM, resolution and service eligibility. Brave Android exposes Widevine support, but hardware security, device software and service policies influence outcomes. A working browser and Widevine support do not establish Netflix/Prime compatibility or 4K/HDR playback on a fork. Treat those as separate device-and-service tests, not MVP guarantees. Brave’s Android Widevine documentation.

Open-source code does not include entitlement to every hosted service. Brave’s build documentation calls out external developers supplying their own service configuration. Audit Safe Browsing, component updates, sync, search integrations and telemetry individually; disable optional integrations or arrange supported endpoints. Dummy values may unblock compilation but do not supply a working production service. Build configuration.

Build and release cost

Use the documented x86-64 Linux build path. Chromium lists at least 8 GB RAM, recommends more than 16 GB, and requires at least 100 GB free disk. My practical allocation would be 32–64 GB RAM and 250–500 GB of free SSD space for a comfortable Brave checkout, outputs and updates; that is a planning allowance, not an official minimum. Full builds can take hours. Chromium Android build instructions; Brave build notes.

Documented build route, to validate during the prototype

Pin the chosen stable tag in a checkout located at <workspace>/src/brave. Follow that tag’s prerequisite and package installation instructions, then initialize for the actual device architecture. Example command shape for an ARM64 target:

pnpm run init --target_os=android --target_arch=arm64
pnpm run build Debug --target_os=android --target_arch=arm64 --target_android_output_format=apk

Install native build dependencies as documented before compilation. Use a release build for meaningful performance measurements. Verify the generated APK’s minimum SDK and supported ABIs against the physical device; its CPU marketing name is not sufficient. These commands have not been executed in this research. Brave Android setup.

Maintenance is a continuing product requirement. Own signing keys, a distinct application ID, CI, release distribution, upstream merges, urgent security updates and a repeatable TV smoke test. Keep the renderer sandbox and upstream security protections intact. Before a public release, rehearse updating the fork to another stable Brave version and measure the conflict burden.

Start with sideloaded test APKs, then pursue Google Play’s TV review. Current TV guidelines require both 32- and 64-bit architecture support and 16 KB page-size compliance from 1 August 2026. Plan to verify release artifacts against these requirements. Google’s policy also prohibits interfering with ads in other apps; the proposed browser scope is its own web content. Store approval remains an external decision. TV distribution requirements; Device and Network Abuse policy.

Keep Fire TV a separate follow-up. Fire OS versions have different Android baselines, and some current Fire TV models use Vega OS. An Android APK is not a universal native deployment strategy for the Fire TV family. Amazon OS/device matrix.

Why Apple TV is a separate decision

Apple’s documentation explicitly lists web views as unsupported on tvOS. WKWebView’s public API availability covers other Apple platforms, not tvOS. Brave’s iOS source therefore cannot simply gain a tvOS target and retain its browsing view. Apple web-view platform guidance; WKWebView availability.

App Store rule 2.5.1 requires public APIs, while 2.5.6 requires the appropriate WebKit framework for browsing unless an alternative-engine entitlement applies. Apple’s published EU and Japan paths concern iOS/iPadOS or iOS respectively; they do not establish a tvOS entitlement. Private API experiments or a custom engine port do not provide an ordinary supported App Store path. App Store rules; EU engine entitlements; Japan engine entitlements.

My recommendation is to exclude a standalone native Apple TV browser from the initial roadmap. AirPlay/mirroring or a remote-rendered browser client could be evaluated later, but introduce another device or server, latency, privacy, media and approval questions. They are different product architectures, not a low-cost iOS port. This conclusion concerns the practical public distribution route, not a claim that no experimental tvOS rendering is technically possible.

A prototype with an explicit decision point

Planning estimate: 1–2 weeks for a bounded technical spike, assuming an experienced Android engineer, access to Chromium build expertise and a suitable Linux machine. Newcomers to Chromium should allow extra ramp-up time.

  1. Establish a baseline: inventory the target TV’s Android API, ABI, memory and input capabilities. Sideload the current official matching APK for compatibility evidence; record startup logs. Build an unmodified pinned source release separately.
  2. Prove the interaction: add the TV launcher entry, complete first run with a remote, and prototype a basic toolbar plus pointer/scroll handling. Finish address entry, navigation, form submission, tab switching and fullscreen video without a mouse.
  3. Prove the inherited behavior: test blocking on controlled resources and representative sites, verify per-site overrides and filter updates, then compare against unmodified Brave on the same device.
  4. Measure the hardware limits: run a 30-minute video/browsing session, sleep/resume, revisit suspended tabs and inspect memory and crashes on one modest and one faster supported TV device.
  5. Decide whether to continue: use a preselected set of about 20 websites covering video, forms, popups, complex scrolling and embedded players. Record which common tasks require unsupported interaction or site-specific hacks.

Continue only if the source build is reproducible, remote-only core tasks are practical, Shields resources update, target-device performance is acceptable, and major sites do not require a growing collection of brittle exceptions. If interaction fails, redesign it before spending time on visual polish. If the build/fork cost is unacceptable, reassess a TV browser with a reusable ad-blocking library as a separately scoped fallback.
